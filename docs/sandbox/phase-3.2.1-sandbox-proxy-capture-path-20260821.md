# Phase 3.2.1 — Sandbox-to-proxy capture path

## Result

The Dockerized HQarroum guest can now reach the workbench proxy through a
session-owned bridge. The emulator remains on isolated container networking;
the fix does not use Docker host networking.

## Root cause

The old path combined an Android/QEMU guest boundary with a Docker boundary:
`10.0.2.2` addressed the emulator container namespace, while the local
`REDIRECT --to-ports 18080` rule did not point at the proxy's actual ephemeral
host listener. Consequently the guest either failed to connect or never
reached the workbench store.

## Implementation

- `SandboxCaptureBridge` is the backend-neutral contract. A lease owns the
  bridge and tears it down on both explicit teardown and drop.
- HQarroum AVD and redroid attach a `ContainerCaptureBridge`.
- The bridge starts the pinned image
  `alpine/socat:1.8.0.0@sha256:a6be4c0262b339c53ddad723cdd178a1a13271e1137c65e27f90a08c16de02b8`
  with `--network container:<emulator>` and listens on guest-visible
  `10.0.2.2:18080`.
- The sidecar forwards to `host.docker.internal:<actual proxy port>`.
- Linux iptables and nftables plans use DNAT to the bridge endpoint, with an
  explicit bypass for the endpoint itself and the existing UDP/443 drop for
  QUIC downgrade.
- Traffic setup probes the endpoint before declaring capture setup successful;
  bridge start, readiness, endpoint reachability, routing, and teardown each
  have separate structured diagnostics.

## Evidence

The live HQarroum run showed:

- sidecar startup and readiness: pass;
- guest endpoint probe: pass;
- emulator network probe through the capture rules: `TCP_PASS`;
- NAT rule: `-A OUTPUT -p tcp -j DNAT --to-destination 10.0.2.2:18080`;
- a bridge run delivered two partial flow summaries to the workbench store,
  proving the guest-to-sidecar-to-host-proxy path was reached.

The first raw probe used origin-form HTTP and therefore did not complete a
flow through the transparent DNAT listener. The proxy listener now normalizes
origin-form requests using their mandatory `Host` header before forwarding
upstream. A wire-level regression test confirms both forms return `200 OK` and
produce paired request/response observations. The harness probe also uses
absolute-form HTTP and reports completed flows separately from TCP acceptance.

## Validation

- `cargo check -p apiaxess-sandbox -p apiaxess-target-apk --test capstone_apkm`:
  pass.
- `cargo test -p apiaxess-sandbox --lib`: 27 passed, 0 failed.
- `cargo test -p apiaxess-workbench-proxy backend::tests::origin_form_is_normalized_and_completes_like_absolute_form`:
  pass; both origin-form and absolute-form returned `HTTP/1.1 200 OK`, with
  two request and two response observations.
- The existing routing test asserts the DNAT target, UDP/443 drop, and proxy
  endpoint bypass.

The Breezy run did not produce a Breezy-specific proxy observation. The two
partial summaries seen in an earlier bridge run were generated by the forced
probe, which the harness executes before launching Breezy; the final Breezy
store had no completed flow and no connectivity-check host. Therefore that run
does not establish an origin-form app failure; the most likely remaining cause
is that Breezy did not fetch without a usable location. The app rerun should
now repeat the forced probe and then inject a concrete location before judging
the weather API path. This phase does not claim that the dynamic-fact thesis is
closed.
