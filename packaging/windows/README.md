# Windows MSI packaging

APIaxess ships as a per-user, x64 MSI. It installs without elevation under the
Windows per-user programs directory, registers with Windows Installer, and adds
one Start Menu shortcut. Uninstall removes the files and shortcut it installed.
The package has no custom actions, service, driver, environment/PATH changes, or
certificate-store operations.

## Build

Prerequisites on the build machine are Windows, Rust 1.88, Node.js, pnpm
11.19.0, and the .NET SDK. WiX itself is acquired as a pinned local build tool;
it is not installed globally.

From the repository root:

```powershell
pnpm install --frozen-lockfile
./packaging/windows/build-msi.ps1
```

The script builds the release engine and GUI, stages the native package layout,
downloads the official Node.js 24.19.0 x64 ZIP, verifies its pinned SHA-256,
pre-caches pnpm for offline use, and fetches + SHA-256-verifies every bundled
tool through the shared pinned manifests — the trimmed OpenJDK
(`fetch-java-runtime.ps1`), apktool + jadx (`fetch-apk-tools.ps1`), and the static
ffuf binary (`fetch-ffuf.ps1`) — staging each at the exact install-relative path
its resolver expects. The WiX authoring is generated by harvesting the whole
stage tree, so the bundled tools are packaged with no `.wxs` edits. It builds:

```text
artifacts/windows/APIaxess-<version>-windows-x64.msi
artifacts/windows/APIaxess-<version>-windows-x64.msi.sha256
artifacts/windows/APIaxess-<version>-windows-x64.build.json
```

Use `-SkipApplicationBuild` only when the release engine and GUI have already
been built. Pass `-BundleFrida` to build the linked `frida-embedded` product
variant: it fetches the pinned Frida devkit, builds `apiaxess.exe` with
`--features frida-embedded` (requires `LIBCLANG_PATH` set for frida-sys's
bindgen), and stages the Frida host components under `frida/`. Build caches and
staging stay under `target/`; release outputs stay under `artifacts/`.

## Installed layout

```text
APIaxess/
├── bin/apiaxess.exe
├── share/apiaxess/gui/       pre-built GUI; no Node needed to serve it
├── runtime/chromium/         verified official Chromium snapshot
├── runtime/node/             private Node + offline pnpm/Corepack cache
├── runtime/java/windows/     shared, trimmed OpenJDK runtime (jlink)
├── tools/apktool/apktool.jar bundled apktool (runs on the shared runtime)
├── tools/jadx/               bundled jadx distribution (runs on the shared runtime)
├── tools/ffuf/ffuf.exe       bundled static ffuf discovery binary
├── runtime-layout.json       stable paths for product-owned runtime launches
└── README.md
```

The runtime is deliberately private: neither installer nor application adds it
to system or user `PATH`. Product code must launch the paths directly. The
browser runtime is official Chromium, hash-pinned during packaging, and is
launched only in a disposable profile.

APK static analysis is fully self-contained: the shared trimmed OpenJDK runtime
plus the bundled apktool jar and jadx distribution are hash-pinned MSI payloads
(staged from `packaging/assets/fetch-java-runtime.ps1` and
`packaging/assets/fetch-apk-tools.ps1`). apktool and jadx are invoked through
the shared runtime by absolute path — never a host `java`, apktool, or jadx.
The bundled static ffuf discovery binary (`tools/ffuf/`, from
`packaging/assets/fetch-ffuf.ps1`) is likewise invoked by absolute path — never
a host ffuf. The optional dynamic-analysis emulator runtime (bundled QEMU +
owned Android-10 image + device-side frida-server, ~2 GB) is deliberately **not**
an MSI payload — it is a separate, optional download installed post-hoc with
`packaging/assets/install-analysis-runtime.ps1` into `<install>\analysis-runtime`
(or an `APIAXESS_ANALYSIS_RUNTIME` override). Until it is present, dynamic runs
report the honest `sandbox.analysis-runtime-missing` diagnostic.

## Installed-product verification

Run the behavioral smoke test against the built MSI:

```powershell
./packaging/windows/test-installed.ps1 `
  -MsiPath ./artifacts/windows/APIaxess-0.1.0-windows-x64.msi
```

The test performs a quiet per-user install into an isolated directory, verifies
every bundled tool (`runtime\java\windows\bin\java.exe`, `tools\apktool\apktool.jar`,
`tools\jadx\lib\*-all.jar`, `tools\ffuf\ffuf.exe`, `runtime\chromium\chrome.exe`)
is present at its resolver path and runs from the install tree (java, apktool and
jadx through the bundled runtime, ffuf directly), confirms `analysis-runtime\` is
absent from the base installer, launches the installed executable, verifies the
packaged GUI and local status API, routes a real HTTP request through the
installed proxy, verifies durable SQLite capture, exercises resend and fuzzer,
runs the private Node and pnpm with Corepack network access disabled, uninstalls,
and compares the Windows root certificate stores before and after. Logs are
retained under the printed `%TEMP%` QA path for diagnosis.

## CI and Linux parallel

The `windows-installer` CI job builds and behaviorally verifies the MSI, then
uploads the versioned MSI, checksum, and build manifest. The `debian-installer`
job does the same for the `.deb` (`packaging/debian/build-deb.sh` +
`test-installed.sh`), which mirrors this layout under `share/apiaxess/` per the
Unix resolver convention. Downloader-managed heavyweight assets (the emulator
analysis-runtime) remain outside both native packages.
